# v5.3 Recognition Quality Review Design

## Goal

Build a read-only recognition quality review layer for product recognition results. The layer helps operators see high-risk fields, missing evidence, inferred-only fields, conflicts, evidence sources, and repeat-recognition stability without changing recognition providers, task state, product confirmation behavior, SQLite schema, or batch/generate/review flows.

## Scope

This first phase implements option A: quality report and display first. It does not block product confirmation, does not auto-correct fields, does not write inferred candidates into confirmed fields, and does not trigger repeated real Provider calls.

The report reads only existing task data:

- `productInfoRaw`
- `productInfo`
- `fieldEvidence`
- `inferredCandidates`
- `visibleText`
- `risks`
- `confidence`
- `recognitionMeta`

## Backend Design

Add `backend/src/services/recognitionQualityService.js`.

The service exports:

- `analyzeRecognitionQuality(task)`: returns a read-only report for one task.
- `analyzeRecognitionStability(results)`: accepts 2-3 stub recognition result objects and returns a stability summary.
- `HIGH_RISK_FIELDS`: `capacity`, `dimensions`, `interfaceType`, `certifications`, `warranty`, `material`, `model`, `brand`, `packageIncluded`, `compatibleDevices`.

Field categories:

- `confirmedWithEvidence`: field has value and reliable evidence.
- `needsManualConfirm`: field has value but evidence is weak, partial, or low-confidence.
- `inferredOnly`: field is only present in `inferredCandidates` or inferred evidence.
- `conflicted`: evidence or repeated recognition results contain different values for the same conflict-sensitive field.
- `blockedHighRisk`: high-risk field has value but no usable non-inferred evidence.

Conflict-sensitive fields in this phase are `capacity`, `dimensions`, `interfaceType`, `warranty`, `material`, `model`, and `brand`. Multi-value fields such as package lists are audited for evidence, but not marked conflicted solely because they contain several values.

`GET /api/tasks/:id` and `POST /api/tasks/:id/recognize` attach `task.recognitionQuality` to their JSON response. This is computed in memory and is not persisted.

## Frontend Design

Add `frontend/src/utils/recognitionQuality.js` for display helpers.

Update `frontend/src/pages/ProductInfoPage.jsx` with a new "识别质量复查" section that shows:

- Field statistics.
- High-risk field audit.
- Missing-evidence fields.
- Conflict fields.
- AI inferred fields.
- Evidence source summary.

The section uses plain Chinese text suitable for operators. It does not block the existing "保存并继续" flow.

## Testing

Backend TDD:

- `recognitionQualityService` generates field statistics.
- It detects high-risk fields.
- It detects missing-evidence fields.
- It detects inferred-only fields.
- It detects conflicted fields.
- It generates evidence source summaries.
- It generates repeat-recognition stability summaries from stub results only.
- It does not mutate task data or `productInfoConfirmed`.
- Existing image-plan tests continue to prove inferred candidates are not used as image copy.

Frontend TDD:

- Utility helpers expose Chinese display sections.
- Product confirmation copy includes "识别质量复查".
- Helpers show field stats, high-risk fields, missing evidence, conflicts, inferred fields, and evidence summaries.
- No helper reports a save-blocking state.

## Safety

This phase does not modify `.env`, read or output API keys, change SQLite schema, change batch/generate/review queues, call real image generation, call real review, upload platforms, or auto-run repeated real recognition.
